# Windows TUN: Local Build 2026092102

Unified VPN `0.0.14`, 2026-09-21. Local work only; not published or installed
over the running application. The previous Android artifact is still build
`2026092101`; no new Android tunnel implementation is part of this change.

## Changes

- Windows VLESS: TCP/RAW (including missing `type`), WS/WebSocket, gRPC,
  HTTPUpgrade, XHTTP/SplitHTTP through the pinned Xray `26.3.27` binary.
  Unsupported transports and combinations produce errors rather than silently
  becoming XHTTP. TUN endpoint pinning retains TLS/Reality SNI, HTTP Host and
  gRPC authority, including original IPv6 formatting.
- Windows AWG: TUN DNS on port 53 is intercepted by sing-box and uses the
  profile's tunnel DNS resolvers over TCP, including private addresses and
  custom ports. Existing proxy-mode rules are unchanged.
- Separate Windows helper: UAC for an unprivileged broker; direct worker launch
  if the broker is already elevated. Both paths retain the same PID/ACL/lease
  validation. The GUI still refuses elevated launch. Invalid, link-local and
  ambiguous endpoint literals are rejected before privileged network work.
- Auto remains Local SOCKS for olcRTC/OpenFlux and System proxy for VLESS/AWG.
  No saved mode is forced into TUN. Android routing behavior is unchanged.

## Completed Checks

- 280 JVM test methods passed, zero failures/errors. Private integration gates
  were unset; these counts are not real-server connection checks.
- Pinned Xray accepted 12 synthetic transport configs using `run -test`.
  Pinned AWG sing-box accepted the synthetic TUN DNS config using `check`.
  Neither command starts a tunnel or uses real credentials.
- Helper: 28 input-validation checks, 6 elevation launch-plan checks and
  6 existing route-plan checks passed. These are non-elevated offline checks,
  not actual UAC or route modification tests.
- Windows package version, isolated JVM startup and bundled native assets
  passed the existing packaging smoke test (8 assets). The extracted TUN helper
  matches the tested generated binary by SHA256. The compiled EXE installer
  passed build identity and same-version replacement policy validation.
- The private update bot separately passed 31 offline tests and tracks stable
  Unified VPN release payloads/builds as well as the upstream projects.

Tests did not change host proxy, routes, DNS, adapters, running VPNs, private
profiles, server services or bot credentials. Active application files under
`desktopApp/build/compose/binaries/main/app` were not replaced; packaging uses
the separate `main-release` directory.

## Not Yet Verified

Real Windows TUN HTTPS, UDP, DNS, IPv6, UAC approval/cancellation, crash cleanup,
sleep and network changes require an isolated Windows VM or test machine.
The helper's READY signal currently confirms local setup, not remote delivery.
There is no persistent kill-switch. Physical-adapter DNS and more-specific LAN
routes remain, so leak-proof routing is not claimed.

Windows TUN for olcRTC/OpenFlux remains unavailable. Both raw SOCKS transports
are TCP-only and OpenFlux additionally requires IPv4 destinations. Jitsi
signaling/ICE/STUN/relay addresses and Yandex redirect/WebSocket addresses are
dynamic: adding only a room-host bypass route would cause routing loops.
The next step needs socket/interface protection in the transport processes or
a verified process-aware TUN layer, followed by a TCP-based DNS bridge and
tests that unsupported UDP/IPv6 does not fall back to a direct connection.
Only after that should TUN be exposed for this profile group.

# Windows TUN: Локальная Сборка 2026092102

Unified VPN `0.0.14`, 21.09.2026. Изменения локальные; публикации и установки
поверх запущенного приложения не было. Предыдущий APK Android остаётся сборкой
`2026092101`; нового туннельного движка Android в этих изменениях нет.

## Что Изменено

- Windows VLESS: TCP/RAW (также при отсутствии `type`), WS/WebSocket, gRPC,
  HTTPUpgrade, XHTTP/SplitHTTP через закреплённый Xray `26.3.27`.
  Неподдерживаемые транспорты и сочетания параметров явно отклоняются, а не
  превращаются в XHTTP. Закрепление IP для TUN сохраняет TLS/Reality SNI,
  HTTP Host и gRPC authority, включая исходное представление IPv6.
- Windows AWG: DNS на порту 53 в TUN перехватывается sing-box и использует
  резолверы профиля по TCP внутри туннеля, включая приватные адреса и
  нестандартные порты. Правила прокси-режима не изменены.
- Отдельный компонент Windows: UAC для обычного broker; запуск без повторного
  повышения, если broker уже повышен. Проверки PID/ACL и владения соединением
  сохранены. GUI по-прежнему отказывается запускаться от администратора.
  Некорректные, link-local и неоднозначные IP отклоняются до изменения сети.
- Auto остаётся Local SOCKS для olcRTC/OpenFlux и системным прокси для VLESS/AWG.
  Настройки пользователя не переключаются на TUN принудительно.
  Маршрутизация Android не изменялась.

## Что Проверено

- Пройдены 280 JVM-тестов, ошибок нет. Доступ к приватным интеграционным
  сценариям не включался; это не проверки соединения с реальными серверами.
- Встроенный Xray принял 12 вымышленных конфигураций через `run -test`.
  AWG sing-box принял вымышленную конфигурацию DNS для TUN через `check`.
  Эти команды не запускают VPN и не используют настоящие ключи.
- Компонент TUN прошёл 28 проверок входных данных, 6 проверок плана запуска с
  повышением прав и 6 прежних проверок плана маршрутов. Они выполняются без
  повышения прав и не доказывают работу настоящего UAC или изменение маршрутов.
- Пройдены проверка версии Windows-пакета, изолированный запуск JVM и
  проверка 8 встроенных нативных компонентов средствами упаковки. Извлечённый
  компонент TUN совпадает по SHA256 с проверенным бинарником. Готовый EXE
  прошёл проверку номера сборки и замены старой сборки той же версии.
- Отдельный приватный бот прошёл 31 офлайн-тест; он теперь отслеживает
  стабильные релизы и файлы сборок Unified VPN, а также исходные проекты.

Проверки не меняли системный прокси, DNS, маршруты, адаптеры, работающие VPN,
приватные профили, серверные службы и секреты бота. Файлы работающего приложения
в `desktopApp/build/compose/binaries/main/app` не заменялись: упаковка использует
отдельный каталог `main-release`.

Файлы находятся в `.downloads/local-artifacts/0.0.14/`; имена, размеры и SHA256
приведены в таблице выше. На GitHub их нет. Первая упаковка EXE не прошла из-за
недоступности Windows Installer для WiX внутри песочницы; отдельная офлайн-сборка
вне неё завершилась с включёнными проверками. Установка не выполнялась.

## Что Ещё Нужно

Реальные HTTPS, UDP, DNS, IPv6, подтверждение/отмена UAC, очистка после сбоя,
сон и смена сети в Windows TUN требуют изолированной VM или тестового ПК.
Сигнал READY означает готовность локальной части, но не доставку на сервер.
Постоянного kill-switch нет. DNS физических адаптеров и более точные маршруты
локальной сети сохраняются; отсутствие утечек не заявляется.

Windows TUN для olcRTC/OpenFlux пока недоступен. Оба исходных SOCKS-транспорта
поддерживают только TCP, а OpenFlux также требует IPv4 назначения. Адреса
Jitsi signaling/ICE/STUN/relay и перенаправлений/WebSocket Яндекса динамические:
обхода только адреса сайта комнаты недостаточно, трафик может зациклиться.
Следующий этап: защита сокетов/привязка к интерфейсу в транспортных процессах
либо проверенный TUN-компонент с правилами по процессам, затем DNS-мост поверх
TCP и тесты отсутствия прямого обхода для неподдерживаемых UDP/IPv6.
Только после этого следует открывать TUN для этой группы профилей.
