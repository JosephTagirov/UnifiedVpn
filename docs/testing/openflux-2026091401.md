The live Android test checked the same app, OpenFlux and DNS-bridge process
identities throughout traffic, plus the Android VPN CONNECTED state. HTTPS ran
as shell UID 2000, outside the app UID excluded from TUN. Both TLS certificates
and nonempty response bodies were checked. The test rejected recovery, fatal
logs, process replacement or a lost TUN. It did not merely accept native Ready.
The private guest profile was removed, app data cleared, and only the owned
emulator was stopped. The live APK used the debug-only control receiver; a
physical-phone test or a live test of the minified release APK is not claimed.
The actual signed release was also exercised offline using real taps/swipes and
the accessibility hierarchy. Screenshot protection produced black frames and
was not bypassed, so pixel-level visual validation is not claimed.

The Windows connection used `DesktopVpnManager`, isolated app data, and its own
authenticated loopback SOCKS. It checked real traffic and removed its owned
native child/runtime config on stop. The final installer launcher was checked
separately; installing over the owner's active Windows application was not done.

## Android Diagnosis

Earlier fresh-emulator attempts authenticated the remote peer, then stopped
before TUN and reported closed/interrupted process-output streams. The test
entry point set AppOps authorization but omitted `VpnService.prepare()`. Android
requires preparation separately from permission before `Builder.establish()`;
without it the builder can return null. See the
[Android VpnService contract](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android15-release/core/java/android/net/VpnService.java).

The debug receiver now calls prepare, rejects missing consent, and returns a
fixed preparation result required by the harness. Production code reports a
null establish result as an error instead of silently remaining Connecting.
The strict retest passed without relaxing log, process, TUN or traffic checks.
Diagnostic-only attempts that filtered a log line are not counted as passes.

Two older common tests assumed SEI was available on every platform. Assertions
now respect the existing Android restriction, with an explicit Android policy
regression test. No olcRTC transport restriction or engine revision was changed.

## Scope And Limits

- One active client per document/key/server, tested sequentially. Existing
  server settings, FI rooms, AWG and Xray were not changed during final checks.
- Host proxy, DNS, routes and the active Windows app were not changed. Windows
  test-child proxy variables and emulator inherited proxy variables were cleared;
  this does not prove reachability on every physical route or mobile carrier.
- TCP/IPv4 only; general UDP and IPv6 are not supported. Mandatory AES-256-GCM
  has no plaintext fallback, but this is not a full security audit or a
  forward-secrecy guarantee.
- Windows TUN remains disabled. No new physical-phone, Android 6, carrier,
  long-soak, Android olcRTC/AWG/VLESS regression or Linux desktop OpenFlux pass
  is claimed. Existing stable-release limitations remain documented.
- Only app binaries, matching native source and checksums are release assets.
  Private profiles, document links, keys and SSH data are excluded. Staged
  source and archive contents were checked locally against known private values
  and credential patterns; this is not a comprehensive security audit.

## Русский

Проверка от 2026-09-15 для `0.0.13`, сборка `2026091401`. Это экспериментальная
версия, не гарантия производственной надёжности. Стабильный канал остаётся на
0.0.12. Отчёт от 13 сентября выше сохранён как история, включая прежние ошибки
Android и короткие замеры скорости четырёх протоколов.

Прошли 234 офлайн JVM-теста и 164 Android host-теста без ошибок и пропусков;
сетевые integration-классы исключались из офлайн JVM-прогона. Также прошли
111 синтетических проверок сценария Android, 17 проверок stdin/контрольных сумм,
18 Python-тестов профилей, 84 теста серверных инструментов и все три Go-пакета
тестов транспорта, Яндекса и аутентифицированного сеанса.

Windows через `DesktopVpnManager` прошёл аутентифицированный SOCKS, проверенный
HTTPS до Instagram и Telegram, повтор через 25 секунд и остановку. Данные
приложения были изолированы. Тестовый процесс и временный конфиг удалены.
Упакованный EXE отдельно прошёл запуск JVM, проверку движков, версии/build и
политики обновления MSI. Установка поверх рабочего Windows-клиента не выполнялась.

Android 35 x86_64 на чистом эмуляторе прошёл аутентификацию OpenFlux, системный
TUN и HTTPS 200 от Instagram/Wikipedia. Проверялись TLS, непустой ответ,
неизменность процессов приложения/ядра/DNS-моста и состояние VPN CONNECTED.
Запросы шли от shell UID 2000, не от исключённого из TUN UID приложения.
Повторное подключение, fatal, смена процесса или потеря TUN отклоняли тест.
Предупреждений чтения логов не было. Профиль удалён, данные приложения очищены,
остановлен только тестовый эмулятор. Сетевой тест использовал debug-only receiver;
проверка физического телефона или живого трафика минифицированного release APK
не заявляется. Подписанный APK отдельно проверен: он не отладочный, сертификат
совпадает с 0.0.12, три ABI и native-библиотеки присутствуют, выравнивание корректно.
На самом подписанном APK офлайн проверены холодный запуск, добавление OpenFlux,
ручные поля, кнопки видимости, прокрутка с клавиатурой и отдельные группы правил.
Падений не обнаружено. Использовались реальные нажатия/жесты и дерево доступности.
Защита снимков давала чёрный кадр и не обходилась; попиксельная визуальная
проверка не заявляется. Этот тест также завершился очисткой и остановкой эмулятора.

Причиной прежних остановок после рукопожатия оказался пропущенный
`VpnService.prepare()` в тестовом входе. AppOps разрешал VPN, но не назначал
приложение подготовленным владельцем. Android мог вернуть null из establish,
после чего очистка закрывала потоки процессов. Документация Android приведена
выше. Receiver теперь вызывает prepare, отказывает без согласия и возвращает
фиксированное подтверждение; сам сервис явно сообщает об отказе создать TUN.
Строгий повтор прошёл без ослабления проверок. Диагностические запуски с
фильтрацией одной строки не засчитываются как успешные тесты.

Два старых общих теста ошибочно ожидали SEI на каждой платформе. Они приведены
к существующему ограничению Android; добавлен явный Android-тест этого правила.
Сами ограничения и версии olcRTC не менялись.

Точные имена, размеры и SHA-256 релизных файлов указаны в таблице выше.
OpenFlux закреплён на указанном коммите; архив включает изменённую обёртку,
транспорт, зависимости и лицензии. Хеши шести native-результатов совпадают
с манифестом, Windows-бинарник внутри приложения совпадает с проверенным входом.
Закреплённые версии olcRTC/AWG/Xray не менялись.

Ограничения: один клиент на документ/ключ/сервер, только TCP/IPv4, без обычного
UDP/IPv6 и Windows TUN. AES-256-GCM обязателен, открытого режима нет; полный
аудит безопасности и прямая секретность не заявляются. Проверки шли по очереди,
без изменения серверных настроек, комнат FI, AWG/Xray, рабочего приложения,
системного прокси/DNS/маршрутов Windows. Прокси-переменные очищались только у
тестовых процессов; это не доказывает доступность у любого оператора.

Новых проверок физического телефона, Android 6, длительной нагрузки,
Android olcRTC/AWG/VLESS или Linux OpenFlux-клиента нет. Прежние ограничения
стабильной версии сохраняются. В релиз входят только приложение, соответствующие
native-исходники и суммы. Личные профили, ссылки, ключи и SSH-данные не включены;
исходники и содержимое архивов проверялись локально на известные приватные
значения и шаблоны credentials, без заявления о полном аудите безопасности.
