# Windows: режимы, интерфейс и переподключения — 16.09.2026

Локальные изменения поверх 0.0.13. Ничего не опубликовано. Рабочий экземпляр
клиента и его сеть во время проверок не переключались. Android и поведение Linux
сохранены; общие компоненты интерфейса получили параметры с прежними значениями
по умолчанию.

## Что изменено

| Профиль Windows | Общая настройка | Доступные режимы | Auto |
| --- | --- | --- | --- |
| olcRTC, OpenFlux | `routingMode` | Local SOCKS, System proxy | Local SOCKS |
| VLESS, AmneziaWG / AmneziaVPN | `externalRoutingMode` | Local SOCKS, System proxy, экспериментальный TUN | System proxy |

OpenFlux использует именно настройку olcRTC, включая переключатель в трее.
Старый TUN в этой группе нормализуется в Auto; проверка выполняется также при
запуске, поэтому обход фильтра интерфейса не включает TUN для этих протоколов.
Настройка VLESS/AWG сохраняется независимо.

На главном экране Windows убрана нижняя кнопка **Add olcRTC location**.
Добавление через верхний `+` сохранено. Под заголовком теперь
**olcRTC, VLESS, Amnezia, OpenFlux**.

## Компонент Windows TUN

В `desktopApp/src/windowsTunHelper` добавлен компонент на штатном .NET Framework
и PowerShell. Игра NightLine к нему отношения не имеет и использует GDScript.
Компонент собирается установленным компилятором Windows, без новых пакетов.

- GUI и протокольные движки работают без повышения прав; отдельный компонент
  запрашивает UAC при выборе TUN и запуске соединения.
- Именованный канал ограничен ACL; обе стороны сверяют PID собеседника.
  Принимаются только порт localhost, учётные данные SOCKS и один IP сервера.
  Пути к программам и произвольные команды по каналу не принимаются.
- Встроенные `tun2socks`, Wintun и фиксированный сценарий извлекаются в каталог
  `%ProgramData%\UnifiedVPN-Tun` с записью только для Administrators/SYSTEM.
  Проверяются владелец, ACL и отсутствие reparse points. Служба не устанавливается.
- IP VPN-сервера определяется до маршрутизации и закрепляется в конфигурации
  Xray/sing-box. Исходные TLS SNI и HTTP Host сохраняются. Для этого IP создаётся
  обходной маршрут; IPv4 и IPv6 направляются в адаптер Olcbox.
- DNS настраивается только у созданного адаптера. Прежние маршруты по умолчанию
  и настройки физических адаптеров не переписываются.
- Остановка отзывает соединение с компонентом; сценарий удаляет созданные
  маршруты. Job Object завершает дочерние процессы при смерти supervisor.
  Незавершённая очистка оставляет защищённый журнал для повторной очистки при
  следующем старте TUN. На этом ПК данный механизм с реальными маршрутами
  ещё не проверялся.

**TUN пока экспериментальный.** Сборка и проверки логики не подтверждают передачу
реального трафика через Wintun, UAC, восстановление после сбоя или отсутствие DNS
и IPv6 утечек. Постоянного kill-switch нет. Реальный тест нужен в отдельной Windows
VM/на тестовом компьютере, чтобы не переключать сеть текущей рабочей сессии.

## Проверки

- JVM-тесты: **244, ошибок 0**. Результаты в `sharedUI/build/test-results/jvmTest`; проверяются
  разделение групп, старые сохранённые значения, недоступность TUN для
  olcRTC/OpenFlux, прежнее поведение Linux и закрепление адреса сервера.
- Компонент: 12 проверок ограничений входных сообщений; сценарий: 6 проверок
  плана маршрутов и допустимого журнала. Все без UAC и изменения сети.
- Windows-пакет создаётся отдельно в
  `desktopApp/build/compose/binaries/main/app/UnifiedVPN/UnifiedVPN.exe`.
  Исходный работающий пакет в `main-release` не заменяется.
- Запуск пакета с `--verify-native-assets`: **8 компонентов проверены**.
  Извлечённый компонент TUN совпал по SHA-256 с итоговой сборкой и прошёл
  самопроверку. Ошибка `Failed to launch JVM` в первом прогоне была вызвана
  недопустимым именем маркера в проверочном скрипте; после исправления имени
  прогон завершился с кодом 0.
- Оконный запуск с вымышленными OpenFlux/VLESS профилями и отдельными APPDATA /
  LOCALAPPDATA: главный экран осмотрен, надпись и удаление кнопки подтверждены.
  Снимки: `build/ui-verification/*/home.png`.
  Программные клики не открыли настройки, поэтому их визуальная проверка остаётся
  ручной; файлы `settings.png` показывают главный экран и не доказывают проверку настроек.
- Ручные подключения к реальным серверам из новой сборки не выполнялись.

Для повторной офлайн-сборки откройте **PowerShell в папке UnifiedVpn**.
Команды используют уже имеющиеся JDK, Go, исходники olcRTC и кэши; ничего не
устанавливают и не переключают сеть. Переменные действуют только в этом окне:

```powershell
$env:GRADLE_USER_HOME = Join-Path $env:USERPROFILE '.gradle'
$env:ANDROID_USER_HOME = Join-Path $env:USERPROFILE '.android'
$env:OLCRTC_REPO = Join-Path $PWD '.downloads\olcrtc-f616-source'
$env:GOPROXY = 'off'
.\gradlew.bat --offline --no-configuration-cache "-Duser.home=$env:USERPROFILE" :sharedUI:jvmTest :desktopApp:createDistributable --console=plain
```

`--no-configuration-cache` нужен из-за уже существующей несовместимости
изоляции JVM-тестов с configuration cache Gradle. Предупреждения об устаревших
API в проекте остаются.

## Что установлено о переподключениях Codex

В журналах есть повторяющиеся ошибки потока `error decoding response body`.
Использовалась цепочка HTTP CONNECT `127.0.0.1:18080` → SOCKS `127.0.0.1:10808`.
Сохранённые режимы обеих групп были LocalSocks. Это не свидетельствует о том,
что обрыв вызван TUN.

| Проверка одного диапазона публичного архива | Результат |
| --- | --- |
| Исходный HTTP CONNECT, 8 MiB при 32 KiB/s | TLS EOF через 166 с, 5 440 584 байта |
| Прямой SOCKS, тот же диапазон | 8 388 608 байт за 260 с; SHA-256 совпал |
| Другой временный HTTP CONNECT relay | TLS EOF через 191 с, 6 269 312 байт |
| Повторное одновременное сравнение исходного HTTP и SOCKS | Оба передали 8 388 608 байт за 256 с; обе контрольные суммы совпали |

Дополнительно выполнен только читающий запрос Codex App Server
`account/rateLimits/read`: через исходный и временный HTTP-прокси он успешен;
прямой `socks5h` в этом клиенте вернул ошибку отправки запроса. Новые генерации
модели для проверки не запускались; значения лимитов и учётные данные не выводились.

**Причина обрывов не доказана, исправление переподключений не подтверждено.**
Замена relay не устранила симптом, временный relay не внедрялся. Его файлы убраны
из NightLine. Текущий launcher Codex, системный proxy, VPN и глобальные настройки
не менялись. Последний сравнительный результат:
`build/proxy-diagnostics/results.json`.

## Что проверить вручную

1. Завершить текущий клиент обычным способом; открыть новый `UnifiedVPN.exe`
   из `main/app` без запуска от администратора. Это отдельная локальная сборка;
   прежние ярлыки всё ещё ведут к прежнему приложению.
2. У OpenFlux и olcRTC проверить одну общую настройку SOCKS/System proxy,
   отсутствие TUN в настройках и цикле трея; переключить профиль и проверить
   сохранение выбора. У VLESS/AWG — отдельную настройку.
3. На изолированной Windows проверить TUN: отмену UAC, передачу HTTPS/DNS/UDP,
   IPv4/IPv6, остановку, смерть GUI/компонента, повторное подключение и отсутствие
   оставшихся маршрутов. Затем проверить восстановление после сна/смены сети.
4. После этого можно оценивать длительные потоки Codex на проверенном соединении.
   Один успешный download не доказывает устранение периодических обрывов.
