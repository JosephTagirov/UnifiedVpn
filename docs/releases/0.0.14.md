# Unified VPN 0.0.14 Preview

Historical local notes for build 2026092201. The publication candidate is
[build 2026092406](0.0.14-build.2026092406.md).

Историческое описание локальной сборки 2026092201. К публикации подготовлена
[сборка 2026092406](0.0.14-build.2026092406.md).

Build `2026092201`, Android and Windows. Experimental prerelease, installed
manually. Stable updates and the private bot's Unified VPN stable-release check
remain on `0.0.12`; they do not offer this preview automatically.

## Changes

- Android's notification profile window stays open after connection results
  and Stop. A separate Reconnect action retries the failed profile, also after
  a rollback to the previous working profile, without starting parallel engines.
- OpenFlux profiles have QR/link sharing from the profile editor, with an
  explicit encryption-key and single-active-client warning. Android also offers
  system sharing and sensitive clipboard copies with scheduled cleanup.
- A guided [server profile helper](https://github.com/JosephTagirov/UnifiedVpn/blob/v0.0.14/tools/openflux-server/CREATE_PROFILE.md)
  prepares a fresh private key, config and importable link from verified installed
  artifacts. Deployment and owned rollback require explicit flags; the default
  action is offline preparation. A separate legacy-editor document is still
  created manually. This helper was tested offline, not on the production server.
- Updated AWG to Throne sing-box `7745e9a` with the `b311c8ac` backend: AWG 3.1
  flags, validated keepalive ranges and a reserved-byte corruption fix. This
  core comes from the development branch `wip/1.14.0`, not a stable release.
- Tested the newest olcbox 1.0.129 core first. Its Jitsi envelope cannot be read
  by an existing `f616` server, so the client uses the preceding compatible
  `d7a00da` instead. OLC2 encryption is unchanged; no server upgrade is performed.
  Android adopts cancellable readiness polling (60s total, 200ms slices) and
  same-room Jitsi settling. See the [upstream report](https://github.com/JosephTagirov/UnifiedVpn/blob/v0.0.14/docs/testing/upstream-refresh-2026092103.md).
- Android's notification profile chooser, main screen and VPN service now share
  one profile repository. Switching from the notification updates the main
  screen; the app icon in the chooser opens Unified VPN. Lock-screen and
  obscured-touch protections remain enabled.
- OpenFlux latency checks use HTTPS through the matching active encrypted
  tunnel, with remote DNS and TLS verification. Inactive profiles ask to
  connect first. Checks do not start a second document client or fall back to
  direct traffic. Edited profiles no longer retain stale ping results.
- Windows VLESS supports TCP/RAW, WS/WebSocket, gRPC and HTTPUpgrade as well as
  XHTTP/SplitHTTP. Server-IP pinning for TUN preserves SNI and HTTP/gRPC identity.
  AWG TUN DNS uses the configured profile resolvers inside its tunnel.
- Windows VLESS/AWG have separate routing settings from olcRTC/OpenFlux and an
  experimental network helper that requests administrator consent for TUN.
  The GUI itself must run normally, without administrator rights.
- OpenFlux server tools support isolated named instances with separate
  documents/keys for multiple devices. Existing instances are not changed
  automatically. Each document still supports one active client.
- The separate private update bot watches OpenFlux, olcRTC, the actual AWG core
  and Unified VPN release builds, in addition to original olcbox and Amnezia VPN.
  Updating only its program preserves credentials, schedule and notification
  history. It never upgrades VPN servers automatically.

## Checks And Limits

- 328 JVM tests, 204 Android host tests, 138 OpenFlux server-tool tests and
  37 notifier tests passed with synthetic inputs. Separate real-connection
  tests are listed below.
- Xray accepted 12 synthetic transport configurations. New AWG binaries passed
  17 WG/AWG/VLESS/DNS-bridge configuration checks; builds for all four targets
  reproduced identical hashes. Seven Jitsi envelope compatibility checks passed.
- Windows olcRTC and AWG reached application-level Connected, passed
  authenticated SOCKS5 + TLS-verified HTTPS to Instagram and Wikipedia, and
  stopped cleanly. The working OpenFlux connection and host proxy were preserved.
- VLESS did not pass the final Windows traffic check: Connected and SOCKS5
  succeeded, but repeated HTTPS TLS EOF/reset errors remained; the last run
  reached only one of two targets. Follow-up isolated native-core checks on
  2026-09-23 passed both HTTPS targets through an explicit OpenFlux upstream,
  but failed directly. Coordinated direct TCP probes were not observed at the
  server capture point; the proxy control was observed. The failing network
  segment is not identified. This is not a direct-VLESS fix or an application
  traffic pass. See the [connectivity report](https://github.com/JosephTagirov/UnifiedVpn/blob/v0.0.14/docs/testing/vless-connectivity-20260923.md).
- Windows helper passed 28 input checks, 6 launch-plan checks and 6 route-plan
  checks. Packaged JVM startup, 8 native assets and the installer's build-aware
  replacement policy passed verification.
- Android native/binding packaging checks and release lint passed. A separate
  fresh API 35 emulator passed eleven synthetic notification/profile/retry/ping,
  OpenFlux share and signed-release upgrade scenarios. APK v1/v2 signatures and all three ABIs
  were verified. All 12 olcRTC/AWG packaging chains, including native stripping,
  were verified. See the [publication verification report](https://github.com/JosephTagirov/UnifiedVpn/blob/v0.0.14/docs/testing/release-0.0.14-2026092201.md).
- Android real traffic on 2026-09-23 used fresh API 35 x86-64 guests and the exact
  hash-verified final debug APK, not the signed release APK. olcRTC and AWG reached
  Connected and guest VPN, stopped cleanly and preserved the app process.
- With the existing Jitsi test profile, the first olcRTC run had TUN DNS errors
  for both targets and failed both SOCKS HTTPS checks. One fresh repeat returned
  Instagram/Wikipedia 200 through TUN and Wikipedia 200 through explicit SOCKS;
  Instagram SOCKS CONNECT was rejected twice.
- AWG returned Instagram/Wikipedia 200 through TUN and Instagram 200 through
  explicit SOCKS on retry; Wikipedia SOCKS TLS closed, then timed out. **Neither
  protocol passed the complete strict Android SOCKS + TUN traffic matrix.**
  TLS verification was retained, with no direct fallback. The harness's
  `socks_authenticated` flag is configuration-derived; native `GoLog` was not
  captured, so readiness/stable process IDs alone do not prove working traffic
  or an uninterrupted transport. Fresh final-build OpenFlux live testing is pending.

**Windows TUN is experimental.** Real TUN HTTPS/UDP/DNS/IPv6, actual UAC
approval/cancellation, crash recovery, sleep and network switching have not
been validated in an isolated Windows VM. READY does not prove remote traffic.
There is no persistent kill-switch or claim of leak-proof DNS routing.

Windows olcRTC/OpenFlux remain Local SOCKS/System proxy only. Android retains
their shared per-app VPN split rules. OpenFlux carries TCP/IPv4, not general UDP
or IPv6. Existing olcRTC server record-layer compatibility requirements remain.
Historical successful server tests are not fresh tests of every private profile
in this build. There is no new Linux binary in this preview.

# Unified VPN 0.0.14: Предварительная Версия

Сборка `2026092201` для Android и Windows. Это экспериментальный выпуск с ручной
установкой. Стабильный канал приложения и проверка стабильных версий Unified VPN
приватным ботом остаются на `0.0.12`: этот preview автоматически не предлагается.

## Изменения

- Окно профилей из шторки Android не закрывается после результата подключения
  и Stop. Отдельная кнопка «Переподключить» повторяет неудавшийся профиль, в том
  числе после возврата к прежнему рабочему, без запуска параллельных движков.
- Из редактора OpenFlux-профиля доступны QR-код и ссылка с обязательным
  предупреждением о секретном ключе и одном активном клиенте. Android также
  поддерживает системное меню отправки и временный конфиденциальный буфер обмена.
- Пошаговый [серверный помощник](https://github.com/JosephTagirov/UnifiedVpn/blob/v0.0.14/tools/openflux-server/CREATE_PROFILE.md)
  создаёт новый приватный ключ, конфиг и ссылку импорта на основе проверенных
  установленных артефактов. Установка и откат своего нового экземпляра требуют
  явных флагов; по умолчанию выполняется только подготовка без сети. Отдельный
  документ старого редактора создаётся вручную. Помощник проверен локальными
  тестами, а не установкой на рабочем сервере.
- AWG обновлён до Throne sing-box `7745e9a` с реализацией `b311c8ac`: параметры
  AWG 3.1, проверяемые диапазоны keepalive и исправление повреждения пакетов при
  обработке reserved bytes. Это ветка разработки `wip/1.14.0`, не стабильный релиз.
- Сначала проверено свежее ядро olcbox 1.0.129. Его формат сообщений Jitsi не
  читается прежним сервером `f616`, поэтому выбран предшествующий совместимый
  `d7a00da`. Шифрование OLC2 сохранено; серверы не обновлялись. На Android перенесены
  отменяемое ожидание готовности до 60 секунд интервалами по 200 мс и задержка
  только для повторного входа в ту же комнату. См. [отчёт](https://github.com/JosephTagirov/UnifiedVpn/blob/v0.0.14/docs/testing/upstream-refresh-2026092103.md).
- Android: окно профилей из шторки, главный экран и VPN-служба используют общее
  хранилище. Переключение из уведомления обновляет главный экран; значок в окне
  выбора открывает Unified VPN. Защита заблокированного экрана и от перекрывающих
  касаний сохранена.
- Пинг OpenFlux измеряет HTTPS через соответствующий активный зашифрованный
  туннель, с удалённым DNS и проверкой TLS. Неактивный профиль сначала нужно
  подключить. Второй клиент документа не запускается, прямого обхода нет.
  После изменения профиля устаревшие результаты пинга сбрасываются.
- Windows VLESS поддерживает TCP/RAW, WS/WebSocket, gRPC и HTTPUpgrade, а также
  XHTTP/SplitHTTP. Закрепление IP сервера для TUN сохраняет SNI и HTTP/gRPC
  identity. DNS в AWG TUN использует резолверы профиля внутри туннеля.
- Windows VLESS/AWG имеют отдельные от olcRTC/OpenFlux настройки маршрутизации
  и экспериментальный сетевой компонент, запрашивающий права для TUN.
  Сам интерфейс приложения нужно запускать обычно, без прав администратора.
- Серверные инструменты OpenFlux поддерживают отдельные именованные экземпляры
  с разными документами и ключами для нескольких устройств. Существующие
  экземпляры автоматически не меняются. На документ по-прежнему один клиент.
- Отдельный приватный бот отслеживает OpenFlux, olcRTC, используемое ядро AWG
  и сборки Unified VPN, сохраняя проверки оригинальных olcbox и Amnezia VPN.
  Замена программы сохраняет секреты, расписание и историю уведомлений.
  Автоматического обновления серверов VPN нет.

## Проверки И Ограничения

- Пройдены 328 JVM-тестов, 204 Android host-теста, 138 тестов серверных
  инструментов OpenFlux и 37 тестов бота на вымышленных данных. Настоящие
  подключения проверяются отдельно.
- Xray принял 12 тестовых конфигураций. Новые AWG-бинарники прошли 17 проверок
  WG/AWG/VLESS/DNS-моста; повторные сборки четырёх целей дали одинаковые хеши.
  Пройдены семь проверок совместимости форматов Jitsi.
- Windows olcRTC и AWG достигли состояния Connected, передали HTTPS
  Instagram/Wikipedia через авторизованный SOCKS5 с проверкой TLS и корректно
  остановились. Рабочее соединение OpenFlux и системный прокси сохранены.
- VLESS не прошёл итоговую Windows-проверку трафика: Connected и SOCKS5
  успешны, но остались повторные TLS EOF/reset; последний прогон прошёл только
  одну из двух HTTPS-целей. Отдельная проверка нативного ядра 23.09.2026 прошла
  обе HTTPS-цели через явно заданный OpenFlux, но не напрямую. Прямые TCP-пробы
  не наблюдались в точке захвата на сервере, а контроль через прокси наблюдался.
  Конкретный проблемный участок сети не установлен. Это не исправление прямого
  VLESS и не успешная проверка трафика приложения. См. [отчёт о соединении](https://github.com/JosephTagirov/UnifiedVpn/blob/v0.0.14/docs/testing/vless-connectivity-20260923.md).
- Windows-компонент прошёл 28 проверок входных данных, 6 проверок плана запуска
  и 6 проверок плана маршрутов. Проверены запуск JVM готового пакета, 8 нативных
  компонентов и замена старого билда установщиком той же версии.
- Android прошёл проверки native/binding-состава и release lint. Отдельная
  проверка на новом эмуляторе API 35 прошла одиннадцать синтетических сценариев
  уведомлений, профилей, retry, пинга, отправки OpenFlux и обновления release. Подписи v1/v2
  и три ABI проверены. Проверены все 12 цепочек упаковки olcRTC/AWG, включая
  stripping. См. [отчёт публикации](https://github.com/JosephTagirov/UnifiedVpn/blob/v0.0.14/docs/testing/release-0.0.14-2026092201.md).
- Реальный Android-трафик проверен 23.09.2026 в новых гостях API 35 x86-64 с
  финальным debug APK, чей точный хеш проверен, а не с подписанным release APK.
  olcRTC и AWG достигли Connected и VPN гостя, корректно остановились с
  сохранением процесса приложения.
- Первый прогон olcRTC с существующим тестовым профилем Jitsi получил ошибки
  DNS обеих целей в TUN и не прошёл обе SOCKS HTTPS-проверки. Один повтор в новом
  госте получил Instagram/Wikipedia 200 через TUN и Wikipedia 200 через явный
  SOCKS; CONNECT для Instagram через SOCKS отклонён дважды.
- AWG получил Instagram/Wikipedia 200 через TUN и Instagram 200 через явный
  SOCKS при повторе; для Wikipedia TLS закрылся, затем истёк таймаут. **Ни один
  протокол не прошёл полную строгую матрицу Android SOCKS + TUN.** Проверка TLS
  сохранена, прямого обхода нет. Флаг `socks_authenticated` выведен из настроек;
  нативный `GoLog` не собирался, поэтому готовность и неизменные PID сами по себе
  не доказывают передачу трафика или непрерывность транспорта. Свежая проверка
  реального OpenFlux итоговой сборки пока ожидается.

**Windows TUN экспериментальный.** Реальные HTTPS/UDP/DNS/IPv6, подтверждение и
отмена UAC, восстановление после сбоя, сон и смена сети ещё не проверены в
изолированной Windows VM. READY не доказывает передачу трафика до сервера.
Постоянного kill-switch нет; отсутствие утечек DNS не заявляется.

Для Windows olcRTC/OpenFlux остаются только Local SOCKS/системный прокси. Android
сохраняет их общую группу раздельного туннелирования. OpenFlux передаёт TCP/IPv4,
но не произвольный UDP/IPv6. Требования совместимости record layer сервера olcRTC
не изменились. Прежние успешные серверные тесты не являются новой проверкой
каждого приватного профиля в этой сборке. Нового Linux-бинарника в выпуске нет.
